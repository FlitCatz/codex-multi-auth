Tracking release: merges the community-submitted `client_version` fix for OAuth model discovery. Runtime behavior is identical to `2.20.0` — whose changelog is included below because v2.20.0 shipped without a GitHub release. (#734; v2.20.0: #732, #735, #731)

## Notes (2.21.0)

- [#734](https://github.com/ndycode/codex-multi-auth/pull/734) independently diagnosed and fixed the same upstream `client_version` requirement reported in [#733](https://github.com/ndycode/codex-multi-auth/issues/733) that [#735](https://github.com/ndycode/codex-multi-auth/pull/735) shipped in `2.20.0`. The conflict resolution kept the already-shipped implementation (stored inventory version preferred, installed `codex --version` as fallback, persisted for the next check), so this merge records the contributor's work without changing behavior.

## Added (2.20.0)

- **First-class Luna Reserve (`gpt-reserve`)**: Codex exposes Luna Reserve as a separately metered backend allowance through the native app-server `account/rateLimits/read` response when the client declares `supportsLunaReserve`. The proxy now parses the official multi-bucket `rateLimitsByLimitId` response, identifies the Reserve bucket by `limitName: "gpt-reserve"`, and registers `gpt-reserve` as a first-class Luna-compatible model with the Luna reasoning ladder and full tool capabilities. `limits --json --refresh` reports an additive `lunaReserve` object — offered/available state, used and remaining percent, window duration, reset timestamp, limit ID, and the normal Luna model slug. An absent bucket reports *not currently offered / unknown*, never 0%. When a Luna model hits a genuine quota 429, routing falls back to `gpt-reserve` without spending reset credits, feeding ordinary quota bookkeeping, or loosening the account pin; transient `requests_too_fast`-style 429s never trigger the fallback. (#732)

## Fixed (2.20.0)

- `codex-multi-auth check` OAuth model discovery no longer fails with HTTP 400 (`Field required: query.client_version`) on fresh installs or stale inventories. The upstream catalog now requires `client_version`; direct discovery sends the stored inventory version when present, otherwise detects the installed `codex --version` (`codex-cli 0.160.1` → `0.160.1`, including through the Windows extensionless npm shim), sends that, and persists it for the next check. No version is hardcoded, because the catalog filters advertised models by `minimal_client_version`. The rotation-proxy path is unchanged — it already forwards the version Codex sent on the inbound request. (#733, #735)
- Responses SSE bodies that arrive without a reliable `Content-Type` (missing or generic) are no longer treated as a single JSON document — which silently produced zero-count usage-ledger rows and skipped stream completion checks. The scanner now sniffs at most the first 4 KiB for SSE field/comment prefixes, reuses the incremental parser, shares the format decision with the OAuth and API/ZDR completion checks, and emits one sanitized debug diagnostic per successful row with missing usage. Valid JSON can never be misclassified, and existing event/JSON memory limits are unchanged. (#731)
